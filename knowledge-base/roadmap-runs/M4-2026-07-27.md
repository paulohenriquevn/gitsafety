# Milestone M4 — Notebooks Jupyter

## Objetivo (do ROADMAP.md)

Cobrir o vetor de vazamento específico do cientista de dados.

## Definition of done (do ROADMAP.md)

- [x] `.ipynb` é lido como JSON; o código das células **e as saídas salvas** são verificados (PRD FR-9)
- [x] O finding aponta a célula e a linha dentro dela, não o offset bruto do JSON
- [x] `.ipynb` malformado → erro específico, sem stack trace
- [x] Teste com notebook real cujo segredo existe **apenas** na saída salva

## Resultado

O blueprint reenquadrou o milestone antes de uma linha de código: um notebook com 5
segredos plantados, varrido pela v0.4.0, já produzia 4 achados. Detectar não era o
problema — **localizar** era. As linhas reportadas eram do JSON, e um notebook aberto no
Jupyter não tem linha 50.

A entrega são 5 de 5 achados, cada um apontando célula e origem (código / saída / anexo /
metadados). O 5º era um valor que o Jupyter parte entre elementos ao salvar.

## O que custou

Cinco rodadas de review independente. Em quatro delas o revisor produziu falso negativo em
código que eu havia declarado pronto — a tabela de `output_type`, a lista de mime-types, o
conjunto de supressão, e a reconciliação entre dois caminhos de varredura.

A lição estrutural: **a cobertura não pode depender da completude de uma lista que alguém
escreveu.** O desenho final varre sempre o arquivo bruto (linha de base incondicional) e
usa o documento parseado apenas para melhorar a localização. Errar no parser custa uma
linha de JSON no relatório, nunca silêncio.

O guard correspondente é fuzz diferencial, não lista de vetores: 901 documentos gerados
por semente fixa, sob a propriedade `achados(.ipynb) ⊇ achados(mesmo conteúdo como texto)`.
Verificado que a guarda é real — sem a linha de base, 143 de 300 documentos perderiam
achados.
